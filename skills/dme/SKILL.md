# DME — Domain-Modeling Engine

## これは何か（そして何ではないか）

DME は「構造判断」という単一のループを、ドメインに依存せず回すエンジン。

- **地形（terrain）** ＝ 任意のドメイン。コードでも、インフラでも、プロダクト提案でも、
  地政学のソース評価でも、文章構成でも。地形は **交換可能** で、DDD はその一例にすぎない。
- **スコープ** ＝ 地形のどこをズームして見るか。地形は広い。全部は見ない。どこを切るかを選ぶ。
- DME はその地形の上で、3 つのモードを **順不同・双方向に行き来するループ** として回す。

「全体像 → 構成要素 → 詳細」と一方向に積み上げる地図ではない。
ループのどこからでも入れて、どこへでも戻れる。

**このスキルがやること**：地形にスコープを当て、観察し、構造・流れの仮説を立て、実態とのズレを読む。
そして「ここは人間が握る」という moat を *明示的に* 立てる。

**このスキルがやらないこと**：moat（① と ③）を勝手に閉じること。
どこを切るか、何をもってズレとするか——その最終判断は人間に返す。
ここを越えて "それっぽい結論" を自信満々に出すと、一番価値のある瞬間
（自動生成された仮説が実態とズレている瞬間を人間が見抜く瞬間）を奪ってしまう。

## 3 モード（順序ではなく役割）

moat はモードそのものではなく、各モードに埋め込まれた **判断** に宿る。
各モードには「AI が主体的に回せる実行部分」と「人間が握る判断部分」があり、後者だけを人間に返す。

### ① スコープ＋観察 — どこを切る・見る 〔観察は共同／枠決めと前提疑いは人間〕
- 地形のどこにズームするか選び（スコープ）、そこを観察する。
- **観察は共同**：Claude が見て、スコープ候補も観察結果も出す。
- **スコープは二層ある**：
  - **初期スコープ**＝人間が投げる。最初に地形のどこを見るか、という枠決め。ここは人間。
  - **操作スコープ**＝投げられた後、Claude が調査のために分解する、その**分解の粒度そのもの**。
    地形に降りるたびに切り直される動的なもの。**ここは Claude が主体的に切ってよい**（実行側）。
- 切り方が変われば見えるものが変わる。**どこを切るか（スコープ）は機械的に決まらない**——
  ここが判断 moat。ただし moat なのは**初期スコープの枠決め**と、後述の**前提を疑う地点**。
  操作スコープの分解は回しつつ、core の確定は人間に返す。

### ② 推測 — 構造・流れの仮説 〔AI が強い側〕
- 観察したものから、構造（登場人物・関係・境界）と流れ（何がどう動くか）の仮説を立てる。
- ここは AI が強い。**Claude が主体的に手を動かしてよい。** 遠慮せず、仮説は複数立てる。
- 仮説は「確定」ではなく「仮説」として出す。次の ③ で検証にかけられる形にする。

### ③ 検証 — ズレを読む 〔まずは共同：照合は AI が強い／基準は人間〕
「検証」は 2 層あり、どちらが moat かが違う。畳まずに分けて扱う。
- **照合（実行部分）＝ AI が強い**：仮説と実態が合うか、矛盾はないか、網羅できているか。
  網羅的・疲れない・反証を自分に当てられるので、しばしば人間より強い。**Claude が主体的に回す。**
- **基準（判断 moat）＝ 人間**：「何をもって _意味のある_ ズレとするか／どの乖離が効くか」。
  照合は機械化できても、どのズレが stakes を持つかは価値判断。Claude は基準の候補を出すが確定は返す。
- ⇒ **まずは共同**。Claude が照合で殴り、人間が基準を確定する。

## ループの性質（水平に行き来し、垂直に再帰する）

**水平 — 順不同で双方向に行き来する。**
- 3 モードは固定パイプラインではない。入口はどこでもいい。観察から始めても、いきなり仮説から始めて検証で殴ってもいい。
- ② で仮説を立てたら ① に戻ってスコープを切り直してよい。
- ③ でズレを見つけたら ② へ戻って仮説を立て直す、あるいは ① へ戻ってズーム位置を変える。

**垂直 — 各モードの中で同じ3モードが再帰する（フラクタル）。**
- 3 モードは横移動だけではない。**各モードの中で詰まったら、その中で ①→②→③ を回す。**
  - ② 推測で詰まったら：② の中でスコープを切り → 推測し → 検証する。
  - ③ 検証で詰まったら：③ の中で同じ3つを回す。
- スケールが変わっても回すループは同じ。だから dme は **全ての手順に対して効く**。
  操作スコープ（①）が地形に降りていくと、各階層で同じループが立ち上がる。

**浮上規則 — どこまで降りるか（自律・無限降下＝トークン暴走を防ぐ）。**
- 降りる前に **exit 条件を1行で宣言**する：「親が詰まっているのは〈X〉。〈Y〉が分かれば親は進む」。
- 降りるのは Y を解くためだけ。子の地形を網羅しない。Y に要る分だけ ①②③ する。
- **浮上判定：「親の詰まりが解ける見込みが立った」瞬間に浮上する。**
  「完璧に分かった」ではなく「**親が進めるだけ分かった**」で止める——これが無限降下を止める肝。
  （地形ごとに形は変わる：ソフト開発なら「実現可能性が見えた」、分類なら「境界が判定可能になった」等）
- バックストップ：降りても Y が解けず子問題が増え続けるだけなら、掘るのをやめ「ここが詰まり」と中間報告で浮上。
- **moat は深さではなく壁の種類**：降りた結果 Y が実現可能性ではなく **価値判断・前提** だと判明したら、
  実行では閉じられない → `⚖️` で人間に返す（前提疑い moat）。**深さの判断は Claude が自律でよい。**

**俯瞰の報酬 — 回すと最初のスコープの外側が見える。**
- ループを回すと構造が掴め、全体を俯瞰できる。すると **見えていなかったものが見えてくる**。
- 最初のスコープの外側・前提に手が届く：「なんでこの要件なのか」「本当に求めているものは何か」
  「このやり方は本当に正しいのか」。
- **この前提への疑問が湧いた瞬間こそ、人間に返す moat**（① の枠決めをやり直す地点）。
  Claude が勝手に閉じず、`⚖️` で表に出して人間に返す。間違ったスコープの内側で正しく答えても価値は無い。

## 不変条件（最優先・moat を奪わない）

**Propose, don't decide. moat ＝ 判断（① 初期スコープの枠決めと前提を疑う地点・③ 何を基準にズレを見るか）。ここは候補を出すが決めない。**

- **判断 moat（① 初期スコープ・前提疑い / ③ 基準）では確定させない**。候補を並べ、最終判断は人間に返す。
- **実行（② 推測 / ③ 照合 / ① 観察・操作スコープの分解）では遠慮しない**。AI が強い側だから主体的に回す。
  仮説は複数立て、照合は網羅的にやる。詰まったらそのモードの中で再帰的に ①②③ を回す。ここで手を抜くと地形が見えない。
- **前提が疑わしくなったら、その地形の中で答えを出し切らずに止める**。ループを回した結果
  「最初のスコープ／要件自体が違うのでは」と見えたら、その疑問を `⚖️` で人間に返す。
- 判断 moat（①③）は飲み込まず、`⚖️` で表に出す。複数の解釈が成り立つなら全部並べる。
- 最後は必ず「あなたが決めるのはここ」と人間に返して止まる。
  人間が ①③ で判断を返したら、それを受けて ② を回し直す（ループ）。

## 出力契約

```
## スコープ＋観察（①）
地形のどこをズームしているか。なぜそこを切ったか。何が見えるか。
（切り方の候補が複数あるなら並べる。core をここで確定しない）

## 構造・流れの仮説（②）
観察から立てた、構造（登場人物・関係・境界）と流れの仮説。複数。

## 検証 — ズレ（③）
仮説と実態のズレの候補。何を確かめればズレが判定できるか。

⚖️ moat（あなたが握る）
- ① どこを切るか：〜で切ったが、〜で切る地形もある。
- ③ 何をもってズレとするか：〜を基準にするか、〜を基準にするか。
  （どちらが正しいかは決めない。トレードオフだけ示す）

→ あなたが決めるのはここ：（①③ を明示的に人間に返す）
```

`⚖️ moat` は **省略しない**。仮説を出すだけで moat を立てないのは、
このスキルの目的（人間が握るべき場所を浮かび上がらせる）を果たしていない。
ループなので、人間が ①③ で判断を返したら、その判断を受けて ② を回し直す。

モードの中で詰まったら、そのモードの中で ①②③ を再帰的に回してよい（出力には畳んで要点だけ返す）。
回した結果「前提・要件自体が疑わしい」と見えたら、それも `⚖️` に上げて人間に返す
（→ あなたが決めるのはここ：に「そもそも〜という要件でいいのか」を並べる）。

## いつ使わないか

- ピンポイントなコード修正（"この関数の型を直して"）
- 短い事実確認（"このコマンドのフラグは？"）
- 答えが一意に定まる質問
こういう時はループを回さず簡潔に答える。地形を広げること自体がノイズになる。

## 例

**Input:** 「Claude の config を global と project でどう分ける？」

**スコープ＋観察（①）：** 地形のどこを切るか。ここでは「設定の責任配置」という層にズームする。
実行レイヤー（runtime の挙動）ではなく、*どの判断をどのスコープに固定するか* という境界が見えている。
（別の切り方もある：「更新頻度」で切れば別の地形が見える）

**構造・流れの仮説（②）：** 観察から、3 分類の仮説——
環境横断で不変（global）／ repo 固有の文脈（project）／ 実行時に変わる（runtime）。
流れの仮説：workflow 定義を global に寄せると環境間で揃うが、repo 固有例外を握りにくくなる。
別仮説：workflow を project に置くと柔軟だが、複数 repo で書き直す重複が出る。

**検証 — ズレ（③）：** この仮説と、あなたの実運用のズレを読む。
「複数 repo を alias で回す」運用がどれだけ均質か？ 均質なら global 寄せ仮説と実態は合う。
repo 固有例外が多いなら仮説はズレる。確かめどころは「例外がどれだけ出ているか」。

⚖️ moat（あなたが握る）
- ① どこを切るか：「責任配置」で切ったが、「更新頻度」で切る地形もある。どちらを見るか。
- ③ 何をもってズレとするか：運用の均質性を、どの指標（例外の頻度？repo 数？）で測るか。

→ あなたが決めるのはここ：workflow の重複コストと、repo 固有例外の握りやすさ、どちらを core に置くか。
あなたが ① で切り方を、③ で基準を返してくれれば、その上で ② の仮説を立て直す。
